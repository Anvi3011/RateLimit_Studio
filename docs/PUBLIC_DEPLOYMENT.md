# Public free demo — prepared, not deployed

This deployment is independent of the AWS Academy account. It uses a Vercel static frontend, one **Free Render web service**, Neon Free PostgreSQL, Upstash Free Redis, and CloudAMQP Little Lemur Free RabbitMQ. No paid worker, paid database, disk, cron job, autoscaling or paid resource is defined in `render.yaml`. Do not upgrade plans automatically. If a listed free plan is unavailable in your account/region, stop and review alternatives; do not select a paid substitute.

The React source, CSS, navigation, charts and algorithms are unchanged. Vercel forwards `/api/*` to Render, so the browser keeps its existing relative fetches, same-origin session cookie and CSV downloads.

## Why the combined service is feasible

`deployment/public/Dockerfile` installs the existing Python dependencies and runs a non-root Python supervisor. It starts exactly three independent processes: one Gunicorn master (one worker, four threads), one outbox publisher, and one RabbitMQ consumer. Flask never starts background processes itself. `PORT` comes from Render.

The supervisor initializes the backend's complete schema with `create_all()` before launching processing roles; it does not drop tables or migrate existing data. Children skip repeated schema initialization. A crashed child is reaped and restarted with exponential backoff. Six consecutive short-lived failures stop the container rather than hiding a crash loop. SIGTERM reaches each child's process group; after a 25-second grace period remaining children are killed and reaped. `/api/live` reads an atomic local supervisor status file and fails if a process is missing or the supervisor is stale. Render uses this inexpensive process check; `/api/health` separately checks all dependencies including PostgreSQL.

The Redis publisher lease allows only one relay to recover shared inflight records, including brief old/new instance overlap during deployment. Connection operations and blocking waits are bounded below its lease. A hard termination leaves unconfirmed messages in Redis inflight; the next lease owner recovers them after at most the 120-second lease interval. A replacement publisher waits without entering a crash loop; graceful shutdown releases the lease immediately. RabbitMQ returns unacknowledged consumer deliveries when its connection closes.

Every consumer delivery checks/inserts PostgreSQL using `ON CONFLICT DO NOTHING` on the existing unique request ID, commits, then updates Redis telemetry, then ACKs. Old Redis markers cannot bypass the database. A crash after commit but before ACK results in a safe redelivery and one SQL row. An infrastructure failure requeues and reconnects with backoff; malformed or invalid records go to the durable dead-letter queue. Redis telemetry is atomic and deduplicated for seven days, but it is not the durable audit count; very old replay can increase operational counters again. SQL history remains unique.

When Render sleeps, **all three processes sleep**. RabbitMQ messages cannot wake it. A visitor's HTTP request wakes the container; processing resumes after startup, initialization and publisher lease recovery. Expect a cold-start delay and eventual, rather than immediate, PostgreSQL history. External services retain data according to their own free-plan policies. Keep the demo to occasional educational use.

## Security and failure behavior

- Public startup requires PostgreSQL and TLS provider URLs, a strong session secret, explicit HTTPS frontend origins, and disabled fault injection. Production never silently falls back to SQLite. The isolated tests use SQLite/fakes only for unit checks, never for the deployed demo.
- Browser cookie stays HttpOnly, SameSite=Lax, host-only and Secure in public mode. CSRF checks remain active. API responses use `Cache-Control: no-store`; Vercel also disables API caching and supplies the existing security policy headers.
- Public mode trusts **zero** incoming forwarding headers rather than guessing the Vercel/Render hop chain. Secure cookies do not depend on a spoofable scheme header. Default header client identity is recommended. IP identity still executes, but groups callers by the Render-facing proxy address within each session; accurate real-IP identity requires separately verified provider header trust.
- `/api/logs/cleanup` is disabled in public mode because it affects multiple visitors. There is no automatic destructive cleanup. Retention extends with session activity, so storage still needs operator monitoring. Review any future cleanup separately.
- Database read errors become generic HTTP 503 responses, rather than successful empty history or raw database error details. Readiness cannot be healthy when PostgreSQL is unavailable. Liveness deliberately does not create sessions or contact databases/brokers.
- Redis/publisher capacity limits and provider outages can still prevent an event from entering the outbox; a failed API enqueue is not guaranteed to yield a SQL row. Finite retry/failed queues also need monitoring. This patch repairs commit/ACK gaps after queue acceptance; it does not claim a cross-database exactly-once transaction for every HTTP response.
- Do not replay a failed/dead-letter queue blindly. Preserve IDs, inspect the SQL request ID first, and retry only under an approved recovery procedure. SQL uniqueness protects history; Redis lifetime operational counters can differ from session SQL totals.

## Free-tier limits and practical workload

Official references checked during preparation: [Render Free](https://render.com/docs/free), [Render Blueprint specification](https://render.com/docs/blueprint-spec), [Vercel rewrites](https://vercel.com/docs/routing/rewrites), [Upstash pricing](https://upstash.com/pricing/redis), [Upstash BRPOPLPUSH](https://upstash.com/docs/redis/commands/list/brpoplpush), [Neon pricing](https://neon.com/pricing), [CloudAMQP plans](https://www.cloudamqp.com/plans/). Recheck terms in your account before creating resources.

- Render Free sleeps after inactivity, has limited memory/CPU and monthly hours/bandwidth/build usage, and does not provide an always-on guarantee. A long cold start can exceed an upstream proxy request timeout; reload after startup. Do not use keep-alive pings as a workaround. Render can also suspend Free services for unusually high service-initiated public-network traffic; this stack contacts external data services, so keep workloads small. If that happens, stop and review free alternatives rather than upgrading.
- Upstash currently advertises 500,000 commands/month and 256 MB. Public publisher idle blocking is 20 seconds and publisher/consumer heartbeats are 30 seconds. This cuts idle traffic substantially but does not make a continuously open dashboard free of quota pressure: unchanged React polls six endpoints every three seconds, with extra log polls. Every simulated request performs many Redis operations. Close demo tabs when finished and monitor command usage. Do not promise unlimited traffic.
- CloudAMQP Little Lemur's published limits include 20 connections, 10,000 queued messages and 1 million messages/month, with idle queue lifecycle rules. Publisher reuses a connection and closes per-event channels. Health/metrics probes still briefly open connections; several browser tabs can increase load.
- Neon Free has storage/compute/transfer limits and database cold starts. Backend uses at most two pooled connections plus zero overflow in public mode, with a separate small worker pool. SQL timeouts use transaction-local settings, avoiding unsupported PgBouncer startup options. Frequent session activity/health/analytics reads can keep compute awake. Missing storage must not be solved by a database reset.
- Traffic and benchmarks remain synchronous HTTP operations, so very large/slow batches can exceed Render/Vercel or Gunicorn timeouts even though the publisher/consumer are separate. Begin with small batches (for example 5–20 requests at 10–50 rps), measure remote latency and increase only within free quotas. A proxy timeout does not imply all already-enqueued events were lost; check SQL history before repeating a batch.
- Provider-specific TLS, Lua execution limits, queue permissions, real forwarding behavior and actual sleep/wake have not been established by local tests. Those are required deployment smoke checks after approval. The static frontend build and real local pipeline checks cannot substitute for them.
